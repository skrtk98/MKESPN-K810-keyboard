# 元ソフト全機能の調査・実機検証台帳

調査日：2026-10-15。対象は既知SHA-256のメーカー配布 `Gaming Keyboard.exe` と、接続中のK810（30FA:2350）。
元ソフトのネイティブ実行は行わず、スキンINI・PE命令・隔離した関数エミュレーションを調べる。
「保存値が一致」と「入力・照明が実際に変わる」は別の検証として記録する。
作業中の台帳であり、全項目の対応・実機検証が完了したことを示すものではない。

2026-10-16以降の元ソフト全体の棚卸し・追加解析は[FULL_REVERSE_ENGINEERING.md](FULL_REVERSE_ENGINEERING.md)に記録する。

## Lightタブ

スキン `skin_color.ini` と `led_normal.jpg`、INIロード `0x41C4CA..0x41D104`、
UI操作 `0x415B80..0x4160C1`、Apply `0x41084F..0x410F8A` を照合した。
本体の設定に照明以外のビットが混在するため、ブロックをゼロ初期化して書き換えてはいけない。

| 項目 | 保存形式／解析状況 | 実機 |

| 速度 | `base+0x18` bit0..2、通常UI範囲0..6 | 未検証 |
| 方向 | `base+0x18` bit6..7、0..3。利用可能な方向はモード依存 | 未検証 |
| 対称表示 | `base+0x19` bit7 | 未検証 |
| 単色・色循環／色選択 | `base+0x19` bit4..6、0が循環、1..7が色番号 | 未検証 |

`lighting.py` に部分編集と読み取り、CLIの `light` / `set-light FILE [--apply]` を実装。
`tools/verify_lighting.py` は13モード・7通りの明るさ／速度・方向等を元PEで生成し、
25ケースを `tests/vendor_lighting_vectors.json` に記録する。RGBのGUI換算は `255-16*n`。
この一致はファームウェアが各モードを実装していることの証明ではない。

## 検証用バックアップと証拠

- 検証前の完全バックアップ：`backups/actions-before-full.json`。
- 追加調査直前：`backups/light-investigation-before.json` と `backups/full-before-deep-tabs.json`。
- これらは利用者固有のためGit管理・公開対象に含めない。
- Windowsの入力監視は `tools/watch_k810_input.py`。K810のVID/PIDが含まれるデバイスパスだけを記録し、他のキーボード／マウスの操作は保存しない。
- [Microsoft Raw Input API](https://learn.microsoft.com/en-us/windows/win32/inputdev/raw-input) に従い、発生元機器ごとに入力を区別する。入力の合成やブロックは行わない。

## 停止条件の訂正

`skin_mac.ini` のボタン10 `SEL_TILL_RELEASE` は `0x416167..0x4161B3` で内部値2、ボタン11 `SEL_TILL_CILICK` は `0x4161B8..0x416204` で内部値1を保存する。初期実装の名称と値を逆にしていた。値1は表ポインタのbit15、値2はイベント数下位byteのbit7へ入る。`tools/verify_extended.py` はこのUI処理も隔離エミュレーションし、名前とシリアライザの組み合わせを検証する。
