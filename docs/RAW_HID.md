# 独自HID入力経路の調査（2026-10-16）

## 確認できた構成

Windowsの `HidP_GetCaps`、`HidP_GetValueCaps` から取得した実機情報。
レポート長はReport IDを含む。

| 項目 | 独自入力 | 設定通信 |
| --- | --- | --- |
| USB VID:PID | 30FA:2350 | 30FA:2350 |
| インターフェース | 1 | 1 |
| Top-level Usage Page / Usage | FF00 / 1 | FF01 / 1 |
| Report ID | 6 | 7 |
| 種類・長さ | Input・3バイト | Feature・8バイト |
| フィールドUsage | FF00 / 2F | FF01 / 20 |
| フィールドサイズ・数 | 8bit × 2 | 8bit × 7 |
| Output | なし | なし |
| その他のレポート | Featureなし | Inputなし |

従って、Report 6の構造は `[06, byte0, byte1]` まで判明したが、2バイトの意味は未同定。
この独自入力領域自体には送信用Output/Featureがない。
有効化コマンドが存在するとしても、設定側のFeature 7等の別経路を検討する必要がある。
Report IDが存在するだけでは、物理操作通知が実装されている根拠にならない。

取得ツール（レポート送信なし）:

```powershell
uv run python tools/inspect_hid_collections.py
```

## 元ソフトの静的解析

追補：[接続ハンドル・間接呼び出し・初期化通信の詳細解析](VENDOR_INPUT_ANALYSIS.md)。

対象PEのSHA256は `ef79b5e0ad1786dd682bc8ed1dad4626627c0518639ec67a702088d6322b8e36`。
Windows上で元ソフトを起動せずに解析した。

- `0x407917..0x40798D` はFF00/1を見つけ、GENERIC_READで開く。
  ハンドルを `0x61F034` へ格納する。
- `0x4079A0..0x407A06` はFF01/1をGENERIC_WRITEで開き、`0x61F030` へ格納する。
  設定の `HidD_GetFeature` / `HidD_SetFeature` は後者を使用する。
- FF00ハンドル保存先への直接参照は、格納・接続成立チェック・マクロ配列と重なる添字付き書き込みのみ。
  このハンドルを読み取りへ渡す処理は発見していない。
- `ReadFile` の直接呼び出しは `0x4640AC` のファイル読み取りラッパー1箇所。
  これをFF00の読み取り処理と結び付ける経路は発見していない。
- `HidD_GetInputReport`、`RegisterRawInputDevices`、`GetRawInputData` の静的インポートはない。
  動的解決の可能性まで完全に否定するものではない。
- マクロ記録開始時 `0x41E192..0x41E1AA` は `WH_KEYBOARD_LL=13` の
  `SetWindowsHookExW` を使用する（コールバック `0x40EA60`）。
  キー指定の捕捉も `0x4284D4..0x4284EC` で同じ種類のフックを使う。
- これまで追跡したFeature送信箇所に、独自入力通知の有効化と特定できる新規コマンドはない。

上記は「配布ソフトでの利用経路が見つからない」という結果。
ファームウェア全体を逆アセンブルして通知機能が存在しないと証明したものではない。
パッケージの `.dat` には既定マクロ等が含まれ、現時点でファームウェアイメージは同定していない。

再現用:

```powershell
uv run --group research python tools/audit_vendor_input.py "research/official/app/Gaming Keyboard.exe"
```

## 実機観測

`tools/watch_vendor_input.py` はFF00/1だけを開き、3バイトのInputを待つ。
Feature/Outputの送信は行わない。K810だけを対象とする通常入力の監視を並行して使い、
操作が認識された時刻と独自通知の有無を突き合わせる。

```powershell
uv run python tools/watch_vendor_input.py --seconds 600 --output research/raw-hid-report6-events.json --stop-file research/raw-hid-report6.stop
uv run python tools/watch_k810_input.py --seconds 600 --output research/raw-hid-standard-events.json --stop-file research/raw-hid-standard.stop
```

2026-10-16の追加調査ではFF00/1を正常に開けた。
`get_input_report(6, 3)` の単発試行では空の結果が返り、有効な現在値は得られなかった。
この結果だけで割り込みInputの非対応を断定しない。
ユーザーが「左上キー→スティック4方向→中央押し込み→ホイール両方向→
中央押し込み→ホイール両方向」を操作した追加試験では、
K810の通常入力を47件取得したのに対し、独自Inputは0件だった。
両監視は同時に動作し、独自側の待機は約258秒。
通常入力には音量のConsumer Control（E9/EAと解放）も含まれる。
操作試験中のEEPROM書き込み・未知の有効化コマンド送信は行っていない。
監視終了後は両ハンドルを閉じた。

この試験は、通常のキー・方向・押し込みによるモード切替・ホイール操作に対して、
既定の動作条件でReport 6の通知が来ないことを示す。
まだ使っていない全コマンドや、全ファームウェア状態を検証したものではない。
未使用の共通設計用レポートである可能性と、別の有効化条件がある可能性を区別できていない。

現段階の結論は「独自コレクションは開けるが、物理操作を受け取る経路は未発見」。
元ソフトに読み取り経路が見つからないため、元ソフトだけの解析から通知有効化を再現する根拠もない。
追加のソフト解析で、接続判定・CFile・キー指定開始・初期化の経路を詳しく追跡した。
次の実機検証では、判明済みの初期化とキー指定コマンドの前後を切り分ける。
ファームウェア本体の入手はさらに調べる方法の一つだが、直ちにそれだけが必要とはしない。

### 既知コマンド・実モードを分けた追加試験

元ソフトの詳細解析後に、次の条件を実機で比較した。
FF00/1は全試験を通して開いたままInputを受信待機し、
Windows Raw InputはK810の通常コレクションだけを記録した。
設定のバックアップを取り、各試験後の248バイトを試験前と照合した。

| 条件 | 通常入力イベント | 独自Report 6 |
| --- | ---: | ---: |
| 既知初期化18/11→18/00後 | 28 | 0 |
| 続けてキー指定用09/40を送信後 | 30 | 0 |
| 別試験で09/C0を単独送信後 | 24 | 0 |
| 押し込みで実際にカスタム側へ移り、最後に既定側へ戻す | 25 | 0 |

キー・スティック・ホイールを比較した。24件の試験は左上キーとホイールのみ。
イベント数は操作回数やマクロの押下・解放にも依存するため、条件間の増減を性能差とは解釈しない。
設定コマンド送信直後を含め、独自側にはレポートが1件も到着しなかった。

**09/C0だけではカスタム割り当ての有効化を確認できなかった。**
左上キーは既定側のEnd（VK35）のままだった。
従って、09/flagsのbit7を単独のモード切替コマンドとして公開してはいけない。
元ソフトの終了時フラグ構築にbit7が含まれることと、それだけで実機のモードが変わることは別。
試験ツールの引数を `--control-bit7-before-capture` に修正し、この制約を記載した。

最後の比較では設定コマンドを使わず、ユーザーが中央押し込みで切り替えた。
最初の左上キーからCtrl（VK17）+F13（VK124）の押下・解放、
ホイールから+120/-120のスクロールを取得し、カスタム側で動作していることを確認した。
再度の押し込み後は左上キーがEnd（VK35）へ戻った。
これにより、「モードが変わったつもりで同じ状態を調べた」という条件混同を避けた。
この比較中もReport 6は0件だった。

終了時は元ソフト由来のフラグ送信・設定通信終了を行った。
コマンド試験2回と物理切り替え試験1回の全てで、248バイトの差分は0。
EEPROMブロック書き込み手順は使っていない。全監視プロセスは終了した。

再現用の状態制御は `tools/probe_vendor_modes.py`。
FF00と通常入力の監視を先に開始し、専用ディレクトリ内のcommand.txtへ
capture / finishを渡して進める。元ソフトの処理を再現する調査用であり、
一般ユーザー向けのモード切替機能ではない。

現段階では、通常操作・初期化・キー指定用コマンド・実際のカスタム側のいずれでも
独自通知を得られていない。既知の元ソフトの経路だけから、ブラウザ専用の入力監視機能を
実装する根拠は得られなかった。未解析の全機能や全コマンドまで非対応と断定はしない。

## WebHIDとの関係

標準キーボード・マウス用コレクションの保護と、FF00の独自入力の有無は別の問題。
独自コレクションが許可され、Inputレポートが送られれば、WebHIDの `inputreport` で受信できる。
現在確認済みなのは設定用Feature通信であり、物理操作の独自通知は未確認。
Web側に待受コードを追加するだけで本体がReport 6を発行するとは限らない。
