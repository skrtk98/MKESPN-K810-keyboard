# マクロ追加フラグと表領域の追加解析

調査日：2026-10-16。K810版の既知SHA256
ef79b5e0ad1786dd682bc8ed1dad4626627c0518639ec67a702088d6322b8e36を対象とする。
元のx86命令を限定実行し、EEPROM書き込みをメモリ上の記録へ置き換えた。
機器アクセス、元アプリの起動、マクロの実行は行っていない。

## マクロ表の「使用数＋2」は何を意味するか

元Applyは41127Dでマクロ表の先頭へ0x64（20枠×5バイト）を加え、
8バイトへ切り上げた位置を最初のマクロ本体の格納先にする。
既知のメタデータ条件では、表先頭1D8→本体先頭240。
一方、4116B0以降で表を書き込む長さは、使用マクロ数Nに対し
`align8((N+2)*5)`と計算される。各使用枠のレコードを作るループはN回だけ。

`verify_macro_table_layout.py`で異なるマクロ番号を持つ合成データを使い、
0/1/18/19/20件と制御フラグを変えた20件の計6ケースを実行した。

| 使用数 | 表の書き込み長 | 表の終了位置（含まない） | 本体との重なり |
| ---: | ---: | --- | ---: |
| 0 | 16 | 1E8 | 本体なし |
| 1 | 16 | 1E8 | 0 |
| 18 | 104 | 240 | 0 |
| 19 | 112 | 248 | 8バイト |
| 20 | 112 | 248 | 8バイト |

表の後に本体が書かれるため、今回の合成データでは最終状態の使用レコードと
各マクロ本体は正しく残った。通常20件のマクロが壊れると確認した結果ではない。
一方、20枠より先の表バイトは独立した有効なレコードではなかった。
表内オフセット100..103にはスタック上の制御フラグ値が現れ、C0→40に変えると
その4バイトもC0000000→40000000へ変わる。残りの一部は後の本体書き込みで置き換わる。

メーカー仕様書に20キー＋2エンコーダーマクロの説明があっても、
この「＋2」だけを根拠に21・22番目の実用マクロ枠と扱えない。
ホイール用2枠の有効なレコードを生成・割り当てる経路は、依然として未発見。
互換実装に、この範囲外の書き出しをそのまま移植しない。

## 内部フラグ+3C

Applyの4115D6..411690と、元UIの416167..41622Bを照合した。
合成した17種類のフラグをApplyへ渡し、15ケースでUI操作時の変化も限定実行した。
使用マクロはAの押下／解放2イベント、繰り返し7回。実際の入力は発生しない。

| 内部値 | 表への反映 | 本体データの繰り返し回数 |
| --- | --- | --- |
| 下位2bit=0 | 継続動作ビットなし | 指定値7 |
| 下位2bit=1 | ポインター上位バイトbit7 | 1へ変更 |
| 下位2bit=2 | イベント数下位バイトbit7 | 1へ変更 |
| 下位2bit=3 | 継続動作ビットなし | 指定値7 |
| bit2 | ポインター上位バイトbit6 | 上の条件に従う |
| bit3..7 | 今回のシリアライズ出力に独立した差分なし | 同上 |

bit2の有無で、イベント本体の押下／解放命令は変わらなかった。
ただし、これはファームウェアがそのフラグを無視するという意味ではない。
従来の記録でreleaseFlagと呼んだ項目は、解放時実行などの意味をまだ実証していない。
資料上の名称をunknownBit2へ訂正し、実動作を決め付けない。

元UIは次のように更新する。

- 「押している間」（ボタン10）：`(元値 & F8) + 2`。bit2を消す。
- 「次回操作まで」（ボタン11）：`(元値 & F8) + 1`。bit2を消す。
- 「指定回数」（ボタン12）：`元値 & F4`。bit2を保持し、bit0/1/3を消す。

従ってbit2付きのデータを読み込んだ場合、指定回数を選び直すだけではフラグが残る。
今回追跡したUIの3分岐から、bit2を新たに1にする処理は見つからない。
ファイル由来の未知フラグを一般的な繰り返し設定へ無断で変換しない。
