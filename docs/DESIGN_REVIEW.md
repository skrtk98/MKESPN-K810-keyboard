# DADS HTMLサンプルとのデザインレビュー

初回レビュー：2026-10-15。対象：`d76a131` の `web/`（feedback版）。下記の指摘本文と行番号は初回レビュー時点の記録。対応後の現仕様は [DESIGN.md](DESIGN.md) を参照する。

## 対応結果（2026-10-15）

| 指摘 | 対応 |
| --- | --- |
| R1 | 接続操作を折り返し可能に変更。高さ不足・小画面は通常のページスクロールへ切り替え、編集欄を固定領域で圧迫しない |
| R2 | `form-controls.mjs`で静的・動的selectの公式ラッパーとchevronを共通化 |
| R3 | input-text・checkbox・form-control-labelの公式CSSと構造を導入。フォーム文字16px、数値は必須入力に統一 |
| R4 | 欄内エラー・aria-invalid・説明参照・修正時解除・該当欄へのフォーカスを実装。不正数値のまま操作行を切り替えない |
| R5 | バナーを通常フローへ移動。全体エラーはモーダル1つにし、重複バナーを残さない |
| R6 | Lightを3作業面、マクロを5作業面へ分割。操作行・照明段階を選んで1つずつ編集。収まらない場合はページスクロールに切り替える |
| R7 | 警告は公式例の三角形と感嘆符、情報・成功は円の各記号に切り替える |
| R8 | 行番号を選択欄と読み上げ名に集約。「変更に追加」等へ短縮し、下書きと本体保存を区別 |
| R9 | 独自CSSを構成ごとに再整理。旧入力テスト・旧タブの規則と未使用CSSを撤去。現仕様と過去の変更記録を分離 |

確認済み：Python 21件・Webプロトコル29件のテスト成功。1280×720、1024×768、768×1024、390×844、320×568、1024×480の全5画面で横はみ出しなし、設定領域内のスクロールなし（収まらない場合はページスクロール）。PCの通常のマクロ行編集は表示領域449px内に収まる。

ショートカット不正値、数値範囲外・空欄、ライブラリ名空欄、修正時のエラー解除、行選択と編集内容の保持、行の追加・並べ替え・削除、照明段階の値の保持、キーボード操作時のフォーカス保持、記録終了後の編集画面への移動、照明パレットの変更追加、通知とナビゲーションの非重複、不正JSONのモーダル、320pxでのモーダル幅、Escapeとフォーカス復帰をブラウザで検証した。デモのみで本体への書き込み・ライブラリへの検証データの保存は行っていない。警告の図形は公式ソースとの静的照合で確認した。

スクリーンリーダー、OSの強制カラーモード、ブラウザの拡大率を使った実試験は未実施。CSSには公式の強制カラー・フォーカス状態を保持している。これらの未実施項目を含めて全適合試験済みとは扱わない。

比較元：[公式リポジトリ](https://github.com/digital-go-jp/design-system-example-components-html/tree/af8b6656c8d864a22ef444d088e5568f3416f6aa)。取得時のmainもこのコミットだった。配布CSS全12ファイルは改行コードを正規化すると公式と一致する。ただし、CSSの一致はHTML構造・利用方法・画面全体の適合を意味しない。

検証：1280×720、390×844、320×568のブラウザ表示。5画面のDOM、計算済みスタイル、メニュー、開閉部品、ショートカット入力エラーを確認。デモのみで、実機への書き込みは行っていない。スクリーンリーダー、OSハイコントラスト、ブラウザ拡大率の実試験は未実施。以下の優先度はこのアプリに対するレビュー判断で、DADS公式の評価等級ではない。

## 修正が必要な点

### R1 / P1：320px幅で接続操作が画面外へ切れる

- 根拠：`web/style.css:139` の画面固定、224・247行付近の接続操作列。320×568ではdocumentのscrollWidthが368px。接続操作列の「接続せずに試す」が右で切れる。Lightの表示領域は142pxしか残らず、保存操作・フッターの固定領域が大きい。
- 影響：狭い画面で操作全体を見渡せず、設定を編集するための領域が極端に狭い。
- 方針：接続操作の折り返しと縮小可能な列を明示する。幅だけでなく利用可能な高さも条件にして、固定保存領域をコンパクトにするか通常フローへ戻す。文字を小さくして収めない。
- 判定条件：320pxで横のはみ出し0。全操作が到達可能で、設定領域を固定要素が押し潰さない。

### R2 / P2：多くのセレクトに公式の矢印とラッパーがない

- 根拠：`web/index.html:80` の操作カテゴリ、107行以降のLight、123行以降のマクロ・ライブラリ、`web/app.mjs:402` 以降の動的マクロ行。公式CSSでappearance:noneになる一方、`.dads-select__control` と `.dads-select__chevron` がない。現在描画されていた17個のselectのうち、公式ラッパーと矢印が揃っていたのはキー・操作とホイール上下の3個だけ。
- 影響：同じ選択操作なのに外見が異なり、Lightやマクロではテキスト入力欄に見える。
- 方針：静的・動的とも公式構造を共通化する。256px上限は割り当て欄のレイアウト指定として維持できる。
- 比較元：[select/playground.html](https://github.com/digital-go-jp/design-system-example-components-html/blob/af8b6656c8d864a22ef444d088e5568f3416f6aa/src/components/select/playground.html)。

### R3 / P2：テキスト・数値入力とチェックボックスが独自実装

- 根拠：`web/style.css:93` の入力欄は角丸4px、左右12px、枠色#1a1a1a。公式input-textは角丸8px、左右16px、枠色gray-600。94行のcheckboxはネイティブ20pxで、公式のサイズ・ラベル・状態構造を使用していない。マクロ行のlabelは98行で14pxとなり、入力自身もfont:inheritによって14pxになる。
- 影響：セレクトと入力の角丸・余白・文字サイズ・状態表現が揃わない。未接続時にも数値入力が白いままで、編集不可が分かりにくい。
- 方針：input-text、checkbox、form-control-labelを必要な範囲で導入する。color入力は別の専用部品として扱い、対応する公式部品がないこと自体を違反とはしない。
- 比較元：[input-text.css](https://github.com/digital-go-jp/design-system-example-components-html/blob/af8b6656c8d864a22ef444d088e5568f3416f6aa/src/components/input-text/input-text.css)、[checkbox.css](https://github.com/digital-go-jp/design-system-example-components-html/blob/af8b6656c8d864a22ef444d088e5568f3416f6aa/src/components/checkbox/checkbox.css)。

### R4 / P2：入力エラーを該当欄に関連付けていない

- 根拠：`web/app.mjs:386` 付近。NotAKeyを割り当てるとダイアログとバナーは表示されるが、shortcut-inputのaria-invalidはnull、aria-describedbyは通常の例示文だけ。確認後のフォーカスはstage-shortcutへ戻る。
- 影響：理由を閉じたあと、どの欄をどう修正するかが画面内に残らない。色・関連付けによる入力欄のエラー状態も伝わらない。
- 方針：入力値の問題は欄の近くへ具体的なエラー、aria-invalid、説明参照を設定し、修正開始時に解除する。通信失敗など画面全体のエラーと分ける。必ずモーダルを出す仕様は見直す。
- 比較元：[input-text/playground.html](https://github.com/digital-go-jp/design-system-example-components-html/blob/af8b6656c8d864a22ef444d088e5568f3416f6aa/src/components/input-text/playground.html)。

### R5 / P2：固定通知がナビゲーション・編集領域を覆う

- 根拠：`web/style.css:383`、392行。通知はPCでtop72px、モバイルでtop12pxに固定され、自動では消えない。入力エラーでは1280×720で640×141pxの通知が上部に重なる。`web/app.mjs:69` では同じエラーをバナーとモーダルの両方へ出し、モーダルを閉じてもバナーが残る。
- 影響：読み取り完了後にも毎回通知を閉じる操作が必要になり、編集とナビゲーションを妨げる。エラーは同じ内容を二度処理する形になる。
- 方針：通常の成功・処理状況は専用の非重複領域で短く表示。画面を止める必要がある障害だけモーダルへ出す。バナーとモーダルを同時に出す場合は役割と内容を分ける。これは公式CSSとの差分というよりアプリの配置・運用上の問題。

### R6 / P2：マクロ画面が最小スクロールの要望を満たしていない

- 根拠：2行のマクロを展開しただけで、PCは表示449px／内容1303px、390px幅は表示455px／内容2472px。ショートカット、単独マウス、記録、手動編集、ライブラリが同じページに積み上がる。Lightも390px幅で表示455px／内容1058px。
- 影響：操作の追加・並べ替え・割り当てを往復する距離が長い。アコーディオンで隠すだけでは、編集中の情報量を減らせていない。
- 方針：マクロは作成方法を選んで該当エディターだけを表示し、ライブラリ管理は別の作業面へ分離する。Lightは基本設定とパレット編集を切り替える。長いマクロは全行同時表示に固執せず選択行を編集する。説明を除去するだけでなく作業単位を分ける。これはDADSの必須規則ではなくユーザー要望に対する評価。

### R7 / P2：警告タイプのアイコンが情報アイコンのまま

- 根拠：`web/app.mjs:70` はwarning色に切り替えるが、75行のアイコンはsuccess／error／その他の3分岐。SVGの外形も`web/index.html:40`で円に固定される。warningは情報用の「i」のまま。
- 影響：公式warning例の三角形と感嘆符による形の区別が失われる。
- 方針：通知タイプごとの公式SVGを使い分ける。見出しにも状況を明記する。静的コードで確認した問題で、非対応ブラウザでの起動分岐は今回実機再現していない。
- 比較元：[warning.html](https://github.com/digital-go-jp/design-system-example-components-html/blob/af8b6656c8d864a22ef444d088e5568f3416f6aa/src/components/notification-banner/warning.html)。

### R8 / P3：番号の反復と長いボタン文言が編集領域を圧迫する

- 根拠：`web/app.mjs:399`、427行は各フィールドに「1. 操作」「1. キー」「1. 待機」を繰り返す。`web/index.html:117` の照明追加ボタンなども長い。
- 影響：行番号とフィールド名の関係を追いにくく、狭い画面で折り返し・ボタン高が増える。
- 方針：行番号は行見出しに1回だけ置く。ラベルは「操作」「キー」「待機時間」。ボタンは文脈に応じ「変更に追加」等へ短くする。本体保存と下書き追加の意味は維持する。「1. 」はこのリポジトリ全体に必須の見出し規則ではない。

### R9 / P3：CSSと設計記録に旧構造が残り、レビューを難しくしている

- 根拠：`web/style.css`には旧dads-tab、panel-tools、panel-test、input-test、open-guide向け規則や同じセレクターへの段階的上書きが残る。`docs/DESIGN.md`にも撤去済み入力監視・旧タブ構造の説明が履歴と現仕様を混ぜて記載されている。
- 影響：新しい変更が過去のメディアクエリに影響されやすく、「公式を使っている」という判断と実際の表示がずれる。
- 方針：公式CSSは維持し、独自CSSをシェル・各画面・状態・レスポンシブ別に整理。現仕様と変更履歴を分離。配布ファイルの改変ではなく上書き側を整理する。

## 維持してよい点

- 公式CSS自体は改変されていない。Noto Sans JP系フォールバック、色トークン、リンクとフォーカスの基本スタイルは読み込まれている。外部フォント配信を使わない判断は、そのままでよい。
- 水平メニューはリンク＋aria-current、モバイルはハンバーガーボタン＋メニューリスト。ARIA tabへ戻す必要はない。
- 使い方のアコーディオンは公式構造を使用。PCの見出しは計算済み18px・太さ400・margin0で、公式スタイルが有効。単独補足にdisclosureを使う区別も妥当。
- エラーモーダルのdialog／header／body／actions構造は公式例に沿う。showModal／closeを直接呼ぶ方式なので、Invoker Commands API用ポリフィルをコピーする必要はない。
- キーボード図は製品固有の部品であり、公式に同等部品がないことを問題としない。押下可能なbuttonと読み上げ名は維持する。
- バックアップと使い方の分離、ページ最下部の短い出典表示、キー選択欄の2段階化は維持してよい。

## 推奨修正順序と確認条件

R1 → R2・R3 → R4・R5・R7 → R6・R8 → R9。
