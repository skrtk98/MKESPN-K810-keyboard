# 元ソフトの独自入力経路・詳細解析

解析日：2026-10-16。今回は実機への列挙・接続・通信を行っていない。
保存済みの配布ファイルを静的解析し、限定したコード範囲をUnicornで検証した。
Win32 APIは全て合成応答に置き換え、元ソフトをWindows上で起動していない。

対象 `Gaming Keyboard.exe` のSHA256：
`ef79b5e0ad1786dd682bc8ed1dad4626627c0518639ec67a702088d6322b8e36`。
既存の旧配布版から展開した同名EXEも同じハッシュだった。

## 接続処理を復元

`407690..407B32` が列挙と接続判断を行う。起動時の呼び出し元は `414934`。
機器通知のハンドラ `413130` からも `41316A` で呼ばれる。
後者は到着 `8000` / 取り外し `8004` のイベントを処理する。

```text
HID GUIDで列挙
 → アクセス権0で検査用ハンドルを開く（61F028）
 → VID/PID、製品文字列、PreparsedData/Capsを取得
 → RegisterDeviceNotificationWで到着・取り外し通知を登録
 → FF00 / Usage 1：
     Capsを624EA8..624EE7へコピー
     CreateFileW(path, GENERIC_READ, share=3, OPEN_EXISTING, flags=0)
     ハンドルを61F034へ保存
 → FF01 / Usage 1：
     Capsを624EE8..624F27へコピー
     CreateFileW(path, GENERIC_WRITE, share=3, OPEN_EXISTING, flags=0)
     ハンドルを61F030へ保存
 → 両ハンドルがINVALID_HANDLE_VALUE以外なら接続成功
```

**RegisterDeviceNotificationWは機器の到着・取り外し通知であり、キー操作の通知登録ではない。**
成功後 `407AAB..407AB8` は `624E3A=4` を入れて `4251A0` を呼ぶ。
この関数は `624E48=1FFF`（EEPROM上限）を設定するだけで、入力スレッドを開始しない。

## ハンドルの参照と間接経路

PEのマッピング全体で `61F034` の4バイト値を検索した。
3箇所が見つかり、全て次の命令のアドレス指定部分だった。
データ領域にこのアドレスを指すポインタ表は見つからない。

| 命令位置 | 命令 | 意味 |
| --- | --- | --- |
| 40798D | mov [61F034], eax | FF00ハンドル保存 |
| 407A0B | cmp [61F034], -1 | 接続成立チェック |
| 427467 | mov [ecx*4+61F034], eax | 1始まりのマクロ情報配列 |

3番目の経路では `427424..427443` が1から空きスロットを探し、ECXは1..20。
最初の格納先は61F038であり、通常のこの経路ではFF00ハンドルへ書き込まない。
前回の監査ツールの「ハンドルと重なる配列」という表現を修正した。

周辺の絶対参照とCaps保存先も検索した。
FF00 Capsの64バイトは16バイトずつ4回ストアされるが、その保存先を読む直接参照はない。
FF00ハンドルをロードして他の関数・スレッドへ渡す直接経路も発見していない。
FF01ハンドルにはGetFeature/SetFeatureへの多数の参照がある。
任意の算術で組み立てたアドレスや動的生成コードまで不存在と証明する形式検証ではない。

## ReadFileの仮想関数表を確認

ReadFile（IAT 5BE350）の直接呼び出しは4640ACの1箇所。
その関数46408Cは仮想関数表5C9D64から参照されるため、直接callの件数だけで除外しなかった。

```text
vtable直前 5C9D28
 → Complete Object Locator 600D74
 → Type Descriptor 621450
 → .?AVCFile@@
```

MSVC RTTIから、この処理は静的リンクされたMFCの **CFile::Read** と確認できた。
ハンドルはオブジェクトの[this+4]から取得し、FF00グローバルは読まない。
CFile(HANDLE)の構築元（4F923E、4F947B等）はファイル用ハンドルをCArchiveへ渡す処理。
アプリ側のCFile構築・終了にはマクロファイル操作があり、FF00ハンドルを渡す経路は未発見。

HidD_GetInputReport、ReadFileEx、NtReadFile、DeviceIoControl、
RegisterRawInputDevices、GetRawInputDataは静的インポートにない。
ASCII/UTF-16のAPI名としても見つからない。
名前の不在だけで動的解決を完全には除外できないので、これ単独を結論の根拠にはしない。

## 入力記録の実装

キー指定開始42849F..4284F1をエミュレーションした結果：

```text
FF01へ SetFeature: 07 09 40 00 00 00 00 00
GetModuleHandleW(NULL)
SetWindowsHookExW(13, callback=427230, module, threadId=0)
```

13はWH_KEYBOARD_LL。コールバック427230..42728CはlParamの構造体先頭から
仮想キーコードを取り、Windowsメッセージ種別と共にPostMessageWで元ソフトへ渡す。
この経路にUSBデバイスの識別やReport 6のデコードはない。
マクロ記録開始41E192..41E1AAも同じ種類のフックを登録し、40EA60がキー情報をマクロ画面へ渡す。

元ソフトのキー記録機能は、独自RAW入力を使っている証拠にはならない。
07/09/40はこのフックと組み合わせる既知コマンドであり、Report 6の有効化とは同定できない。
この設定でファームウェアの出力先が変わるかは、別の未解決事項として残る。

## 接続直後の通信

非代替モデル分岐414B2D..414B80とパケット構築関数413030のエミュレーション結果：

```text
FF01へ 07 18 11 00 00 00 00 00
10ms待機
FF01へ 07 18 00 00 00 00 00 00
```

その後は既知のFeature 7メタデータ取得へ進む。
この初期化範囲にもFF00からのReadFileやInputレポート取得はない。

## 再現方法

```powershell
uv run --group research python tools/audit_vendor_input.py "research/official/app/Gaming Keyboard.exe"
uv run --group research python tools/verify_vendor_connection.py "research/official/app/Gaming Keyboard.exe"
```

前者は参照・RTTI・代替API名を調べ、後者は次の6ケースと入力捕捉開始・初期化通信を検証する。
未知の実行先への分岐はエラーにする。どちらもhidapiを使わず、実機を開かない。

| 合成条件 | 結果 |
| --- | --- |
| FF00だけ開いた | 列挙継続 |
| FF01だけ開いた | 列挙継続 |
| FF00取得済み→FF01を開く | 接続成功 |
| FF01取得済み→FF00を開く | 接続成功 |
| FF00だがUsage=2 | 開かず列挙継続 |
| FF00取得済み、FF01のOpen失敗 | 列挙継続 |

6ケース全てでFF00ハンドルのメモリ読み取りは407A0Bの比較だけだった。

## 結果から導く次の調査条件

「FF00を開くので、どこかで操作入力を読んでいるはず」という仮説は支持されない。
**FF00を接続成立条件として確保するが、このソフトでは受信に使用しない**という解釈が
今回のコードと最も整合する。共通ソフト由来の未使用経路かもしれないが、開発意図は推測。
ファームウェアがReport 6を発行できないことを証明したものではない。

今後の実機確認は、元ソフトに根拠がある条件を分けて行う。

1. 接続初期化（18/11→18/00）前後でReport 6が発行されるか。
2. キー指定時の09/40前後で、標準入力とReport 6の出力先が変わるか。
3. 既知の終了処理で状態が戻るか。EEPROMの維持も別途照合する。

これは今後の検証条件であり、今回は実機へ送信していない。
未知コマンドの総当たりより先に、既知の元ソフトの状態遷移との対応を調べる。

後続の[実機比較結果](RAW_HID.md)では、初期化後28件・09/40後30件・
09/C0後24件・物理切替によるカスタム側比較25件の通常入力を取得したが、Report 6は全て0件。
09/C0単独ではカスタム側へ切り替わらなかったため、これを単独のモード切替とする解釈は採用しない。
物理切替ではCtrl+F13とEndの違いで実モードを区別した。

## 画面上のキー表示は何を検出しているか

追加調査では、実機の押下追従表示、図のマウス選択、入力されたキーの表示を分けた。
元ソフトに入力キーを表示・記録する処理はあるが、それだけでは独自RAW経路の存在を意味しない。

### メイン図のホバー・押下表示

MFCメッセージ表（5BF858から57エントリー）に以下の対応がある。

| Windowsメッセージ | ハンドラ |
| --- | --- |
| WM_MOUSEMOVE（200） | 41AF50 |
| WM_LBUTTONDOWN（201） | 415A40 |
| WM_LBUTTONUP（202） | 416730 |
| WM_PAINT（0F） | 41B240 |
| WM_TIMER（113） | 403200（retのみ） |

マウス移動ハンドラは引数のPOINT座標を40C380へ渡す。
40C380は配置矩形に対してPtInRectを呼び、該当する画面領域の番号を返す。
その結果を41AFA8で61F0E8へ保存する。表示を更新する値はUSBのキー位置ではなくマウス座標から得た番号。

WM_LBUTTONDOWN経路の415B17が63B988を1へ、WM_LBUTTONUP経路の4167AFが0へ戻す。
描画420DC0..は61F0E8で指定された領域と63B988を読み、オーバー／ダウン用の画像を選ぶ。
41BA19..41BA2Dで、その画面領域番号が描画関数へ渡されることも確認した。
したがって、この「押されている」画像は**マウスで図を押している状態**として説明できる。

61F0E8への値設定はマウス移動による領域番号の設定とFFへのクリア、
63B988への書き込みはマウス押下・解放と初期化／画面遷移であり、
実機キーイベントからこれらを更新する経路は発見していない。
メインのメッセージ表にWM_INPUT・WM_KEYDOWN・WM_KEYUPの直接登録はない。
ただし、これ単独ではPreTranslateMessageなどの別経路を否定できないため、下記の入力表示も追った。

### キー指定欄・マクロ記録欄

- キー指定のメッセージ処理429340は、捕捉中のフラグ648FE8を確認する。
  Windowsのキー押下／解放メッセージから仮想キーを変換し、[this+D58]の文字列を更新して再描画する。
- マクロ記録のメッセージ処理423170は、記録中のフラグ63B9A8を確認する。
  同じくWindowsのキー押下／解放メッセージからキーコードを取り、マクロ内部データへ追加する。
- これらへ入力を送るのは前述のWH_KEYBOARD_LLのコールバック。
  デバイス識別や物理行列位置は含まれず、K810以外のキーボードからの入力も対象になり得る。

全体の追加解析では、444859にもWH_KEYBOARD_LL（13）の登録を確認した。
これは649108へフックを保存する別ダイアログで、コールバックはキー指定と同じ427230。
4448E0側にUnhookWindowsHookExと649108のクリアがある。
したがって、アプリ固有の低レベルキーボードフック登録箇所は2か所だけではなく3か所。
いずれもWindowsの仮想キーを扱い、FF00の読み取りルートにはならない。
ほかに検出した44C732/4595EE/45A50D/48E209のフック種別はそれぞれ-1/7/5/7で、
13の低レベルキーボードフックとは区別する。全API参照の一覧はaudit_vendor_input.pyで再現する。

確認できた範囲では、「入力されたキーの表示・記録」はあり、
「K810の物理キーを個別に識別してメイン図へ押下を反映する機能」は未発見。
仮にVKと既定配列を対応させる表示を作っても、割り当て変更後の物理位置や入力元機器の一意識別は保証できない。

再現用（USBアクセスなし）:

```powershell
uv run --group research python tools/audit_vendor_ui_input.py "research/official/app/Gaming Keyboard.exe"
```

この結果は静的解析による機能の切り分けであり、元ソフトを実行して全画面の挙動を確認したという意味ではない。

## チップメーカー参照ソフトとの比較

後続の[CHIP_REFERENCE.md](CHIP_REFERENCE.md)では、K201メーカー公開の参照ソフト2種類も
別バイナリとして取得・静的解析した。両方ともFF00を開くが、ハンドルのコード直接参照は
保存・接続判定等に限られ、独自入力の受信経路は見つからない。
参照01に多いReadFile呼び出しはCランタイムのテキスト変換処理等と対応した。
K810版だけの探索漏れを減らす比較結果であり、ファームウェアのReport 6が永久に送信不能という証明ではない。
